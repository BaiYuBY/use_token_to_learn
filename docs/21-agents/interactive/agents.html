2错误会累积：步数越多，越容易失败Errors compound: more steps, more failures

三种错误各占约三分之一：参数格式错（循环把校验错误返回给模型，它重试就好）、标题拼错（工具说“没有这篇文档”，同样可以重试）、直接编一个答案（循环结束，答错）。只有最后一种是致命的，所以每次模型调用“致命出错”的概率约为 0.3 × 错误率，成功率大约是 (1 − 0.3e)模型调用次数。作答前的自检拦下了大部分编造的答案。 The three mistakes are about a third each: malformed arguments (the loop returns the validation error and the model retries), a misspelled title (the tool says “no such document”; again a retry), and a made-up answer (the loop ends with a wrong answer). Only the last is fatal, so each model call fails fatally with probability about 0.3 × the error rate, and success is about (1 − 0.3e)model calls. The self-check before answering stops most made-up answers.

3上下文成本：每次调用都要重读整段对话Context cost: every call re-reads the conversation

模型没有记忆：每一步都要把系统提示、工具说明和到目前为止的全部对话重新发一遍。所以总读入量随步数超线性增长；其中很大一块是每次都一样的系统提示和工具说明，这正是提示缓存（13 章）发挥作用的地方。删掉没用的工具结果能省一点；把互不依赖的调用一次发出（并行工具调用）能少几个来回。 The model has no memory: every step re-sends the system prompt, the tool descriptions and the whole conversation so far. So the total grows faster than the number of steps, and a big share is the system prompt and tool descriptions, identical every time: exactly what prompt caching (chapter 13) is for. Dropping useless tool results saves a little; sending independent calls together (parallel tool calls) saves round trips.

4手写循环 ↔ LangChain / LangGraphHand-written loop ↔ LangChain / LangGraph

code/langgraph_agent.py 用 LangGraph 实现了同一个 agent，在 120 个任务上与手写循环走出完全相同的工具调用序列。框架没有改变循环本身，它提供的是：现成的部件、可视化的结构、持久化的状态和人工介入。 code/langgraph_agent.py builds the same agent in LangGraph; on 120 tasks it makes exactly the same sequence of tool calls as the hand-written loop. The framework doesn't change the loop; it adds ready-made parts, a visible structure, persistent state and human-in-the-loop.
